# Research Log — Can an external website learn the Instagram account of a bio-link clicker?

Question: when someone taps the public link in an Instagram profile bio, can the
independent destination website — using only publicly documented, legitimate,
reproducible web observability — determine the clicker's Instagram username,
numeric user ID, or any account-level identifier?

Method: adversarial falsification. Assume "impossible" is wrong; try to break it.
Every lead below is labeled with status, exact observability, who it identifies,
reproducibility, evidence, and limitation. Sharer vs Clicker kept strictly separate.

---

## LEAD 1 — `igsh` / `igshid` URL parameter
STATUS: Confirmed observable / does NOT identify the clicker.
WHAT IS OBSERVABLE: parameter on links generated/COPIED inside Instagram
(`instagram.com/p/.../?igshid=MzRlODBiNWFlZA==` → base64 of a 40-bit hex number).
WHO IT IDENTIFIES: a SHARE SESSION (sharer-side event), not an account, not a clicker.
REPRODUCIBILITY: copy the same post twice from the same account → different values
⇒ per-share token, not per-account. Decode: base64 → hex (e.g. `34e80b5aed`).
EVIDENCE: r/privacy PSA (reddit.com/r/privacy/comments/1kdo2w8); Stack Overflow
62275124; r/AskProgramming 15gtj70 (decoding reproduced by multiple users).
LIMITATION: generated by Instagram for links IT generates; a plain bio URL typed by
the profile owner carries no igsh at all. Even when present it is an opaque internal
token — no public API maps it to a username. It can at most fingerprint the SHARE,
and the sharer here is the profile OWNER, not the visitor.

## LEAD 2 — `l.instagram.com` redirect wrapper (`u`, `e`, `s` params)
STATUS: Confirmed observable (version-dependent) / opaque.
WHAT IS OBSERVABLE: bio-link clicks historically hop through
`https://l.instagram.com/?u=<target>&e=<opaque token>&s=1` (visible via server-side
redirect chain or sometimes as Referer).
WHO IT IDENTIFIES: UNKNOWN — `e` is an opaque, presumably encrypted/signed internal
token, plausibly about the click context on Instagram's side.
REPRODUCIBILITY: click a bio link, inspect server logs (this system's raw request
inspector does exactly that).
EVIDENCE: matomo-org/matomo#15902 (real URLs, maintainers treat `e` as potential
PII and strip it); webmasters.stackexchange.com/a/114165.
LIMITATION: even in the best case for a researcher, `e` is UNDECODABLE by an external
site — it is a handle Meta can resolve, not you. Logging it gives you a random-looking
string you cannot map to any account. A token being account-correlatable-on-Meta's-side
is fundamentally different from a website-readable identifier.

## LEAD 3 — `X-Requested-With: com.instagram.android` header
STATUS: CURRENT / REPRODUCIBLE (removal was SUSPENDED by Chrome team).
WHAT IS OBSERVABLE: Android WebView auto-sends the host app's package name.
WHO IT IDENTIFIES: the APPLICATION (identical for every Instagram user on Android).
REPRODUCIBILITY: our test server logs it (verified in simulation).
EVIDENCE: android-developers.googleblog.com 2023 announcement; chromestatus feature
5160086884843520 "suspended — we've ended the experiments"; r/reactnative 2026 confirming
still sent.
LIMITATION: zero account information. Account A vs Account B on the same phone:
byte-identical header.

## LEAD 4 — Instagram WebView User-Agent
STATUS: CURRENT / REPRODUCIBLE.
WHAT IS OBSERVABLE: UA contains `Instagram <version> Android` (+ device model, DPI,
locale) on Android; `Instagram/<version>` on iOS.
WHO IT IDENTIFIES: app version + device context. Not the account.
EVIDENCE: user-agents.net real capture strings; stackoverflow 76396835 (UA varies
slightly per request — session-random components, NOT account-linked).
LIMITATION: switching accounts changes nothing; changing device changes everything.
Confounds any naive "signal" claim.

## LEAD 5 — Referer behavior of the in-app browser
STATUS: CURRENT / REPRODUCIBLE.
WHAT IS OBSERVABLE: Referer is stripped or rewritten (l.instagram.com) by the
in-app browser; traffic often appears as "Direct" in analytics.
WHO IT IDENTIFIES: nobody — absence of signal.
EVIDENCE: flyn.to/blog/instagram-in-app-browser; MDN Referer docs.
LIMITATION: none to exploit; matters for experiment design (don't expect reliable
referrers from IG).

## LEAD 6 — Meta `pcm.js` injection into the in-app browser (Krause 2022)
STATUS: CURRENT/HISTORICAL marker — detectable; exact behavior varies by app version.
WHAT IS OBSERVABLE: Instagram/Facebook iOS apps inject
`https://connect.facebook.net/en_US/pcm.js` after probing for `iab-pcm-sdk`; also
registers text-selection listeners. Our client.js passively detects this injection.
WHO IT IDENTIFIES: NOBODY — for the WEBSITE. It is a bridge that lets META track the
user on OUR site. The direction is reversed: Meta can correlate the visit with the
IG account (they own both contexts); the website receives no account data.
EVIDENCE: krausefx.com 2022 analysis with exact injected commands; inappbrowser.com
tooling; Meta spokesperson response (Andy Stone) acknowledging injected code for
"aggregating events".
LIMITATION: this is the single strongest documented IG-account↔external-visit link —
and it exists ONLY inside Meta's systems. No documented case of pcm.js exposing the
username/user-ID to page JavaScript.

## LEAD 7 — LocalMess / "Bridges to Self" (USENIX Security '26)
STATUS: HISTORICAL / FIXED-IN-PROGRESS — the closest thing to a real web↔IG-account bridge.
WHAT IS OBSERVABLE: Meta apps listened on localhost ports (e.g. TCP 12387); Meta
Pixel scripts on ordinary websites passed the `_fbp` web cookie to the local app
(WebRTC SDP munging), letting Meta deterministically merge web cookie ↔ native app
account identity server-side. Defeated Incognito, cookie clearing, VPNs.
WHO IT IDENTIFIES: the CLICKER (device-level web↔app identity merge) — but only
for META's benefit. The website's data flows INBOUND to Meta; nothing account-level
flows back to the site.
REPRODUCIBILITY: was reproducible in all major browsers pre-patch; now defended
(Chrome restricted ports + Local Network Access permission in Chrome 142; Brave
blocks localhost requests; Meta terminated the campaign after responsible disclosure).
EVIDENCE: localmess.github.io USENIX Security '26 paper (full measurement + disclosure
timeline).
LIMITATION: (1) direction is one-way — never returns the IG username to the site;
(2) requires embedding Meta Pixel, i.e. a third-party tracker (violates this
project's privacy constraints); (3) fixed/mitigated as of 2025-2026. Verdict: does
NOT solve the click-only problem, but is prime evidence that the web↔account
correlation problem is solved only by the platform itself, from the inside.

## LEAD 8 — WebViewTracer (NDSS 2026), Java→JS information diffusion
STATUS: Confirmed research evidence — app-side injection is real, IG-specific finding negative.
WHAT IS OBSERVABLE: at scale (10K apps), apps inject Ad IDs, locations, sometimes
account names into their WebViews. For Instagram specifically: extracts image URLs,
logs clicks + scroll depth (`enableVerticalScrollDepthLogging`). No injection of
IG account identifiers INTO pages was found.
EVIDENCE: cs.uic.edu NDSS 2026 WebViewTracer paper (Table IX lists Instagram).
LIMITATION: confirms the asymmetry — IG harvests FROM the page; it does not publish
account identity TO the page.

## LEAD 9 — Identity-resolution vendors (LiveRamp, MAID/HEM matchers, etc.)
STATUS: Confirmed NOT APPLICABLE to the click-only problem.
WHAT IS OBSERVABLE: nothing — these systems require PII inputs (email, phone,
name+address, MAID, CRM IDs) or already-collected first-party cookies. Match rates
(55-85%) are quoted against PII keys.
EVIDENCE: docs.liveramp.com identifier docs; liveramp RampID methodology (resolves
emails/addresses/phones); vendor match-rate literature.
LIMITATION: no publicly available identity graph takes "an ordinary anonymous
Instagram WebView visit" and returns the visitor's IG username. The claim would
require inputs the clicker never provided. Marketing language ≠ verified I/O.

## LEAD 10 — Instagram session cookies inside the WebView (boundary check)
STATUS: NOT observable — security boundary (documented).
WHAT IS OBSERVABLE: nothing. WKWebView keeps per-app cookie stores; even the IG
WebView's instagram.com cookies are instagram.com-origin cookies — same-origin
policy blocks any external site from reading them. On Android, WebView cookie
store is likewise app-scoped.
EVIDENCE: Apple WKWebView/HTTPCookieStorage docs (per-instance cookie storage).
LIMITATION: reading them would be cookie theft — prohibited by this project's
constraints and by browser security. Listed to close the loophole question honestly.

## CONTROLLED EXPERIMENT PROTOCOL (built into this system)
The raw request inspector records: method, path, query params, minimized headers
(UA, Referer, X-Requested-With, client hints…), visitor ID, IG-in-app flag, plus the
client beacon (languages, tz, screen bucket, connection, pcm_injected).

TEST MATRIX (use ONLY your own accounts/devices):
- T1 Same phone, IG Account A → tap bio link ×5 (log each).
- T2 Same phone, IG Account B → tap bio link ×5.
- T3 Different phone, Account A (where possible).
- T4 IG in-app browser vs T5 external browser (same phone).
- T6 Logged-in vs T7 logged-out (where IG allows).

CENTRAL QUESTION: does ANY website-visible signal change consistently with the
account while device/browser are held constant?
Candidate fields: `l.instagram.com` `e` token (if present), query params, headers.
Before accepting any signal as account-linked, rule out: session randomness (compare
repeats within T1 — if it differs click-to-click it's session noise), app version,
A/B buckets, network changes, time, cache. A signal is only "potentially
account-linked" if it is (a) stable within an account, (b) different across accounts,
(c) reproducible across days. Expected per all documented evidence: no such signal
exists; `e` (when present) is session-random and undecodable regardless.

## CONCLUSION
NO VERIFIED CLICKER-TO-INSTAGRAM-ACCOUNT BRIDGE FOUND.
"not found" ≠ "impossible": the correlation demonstrably EXISTS inside Meta's own
systems (pcm.js bridge, LocalMess) — but every documented mechanism either (a) flows
inbound to Meta only, (b) is opaque/undecodable externally, (c) identifies sharer/
app/device rather than the clicker, or (d) was fixed. For an independent website
using only legitimate, publicly documented observability, the account boundary
holds. Deterministic linking remains available ONLY through voluntary, explicit
user identification (login/OAuth) — which this site deliberately does not require.
